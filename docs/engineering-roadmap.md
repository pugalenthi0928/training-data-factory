# Forge engineering roadmap

## Target

Forge should become a credible, inspectable training-data release system. The
portfolio claim is not that Forge can generate examples. Many scripts can do
that. The claim is that Forge can turn source material into a versioned dataset
whose lineage, quality decisions, evaluation boundaries, and release evidence
can be inspected and reproduced.

The project reaches the target only when a reviewer can answer these questions
from public evidence:

1. What source produced each record?
2. Which transformations and models touched it?
3. Why was the record kept, rejected, or assigned to a partition?
4. Can any source or semantic duplicate cross an evaluation boundary?
5. Which measurements are automatic, which are model judgments, and which were
   calibrated against people?
6. Can the same release be verified after it is downloaded?
7. Can a fresh user run a meaningful workflow without reading the code first?

## Current audit

### Strong foundations

- Document and chunk identifiers are deterministic and content-derived.
- Train and test assignment is grouped by source document.
- Split manifests record source overlap, counts, seeds, and artifact hashes.
- A supplied benchmark is mandatory and lexical contamination can block a run.
- Statistical procedures are named accurately and tested.
- The repository has linting, type checking, property tests, coverage gates,
  and a no-install browser demo.
- Historical evidence limitations are disclosed instead of hidden.

### Remaining weaknesses

- The public demo exercises deterministic controls, not the real Python
  pipeline or a hosted processing service.
- Exact, MinHash LSH, Jaccard, and optional embedding controls are implemented.
  Production embedding thresholds still require corpus-specific human calibration.
- The judge calibration framework is implemented and exercised on controlled
  fixture labels. Genuine human review has not yet been collected.
- Source license, permitted use, structured identifier risk, and record-level
  rejection reasons are release evidence. The privacy detector is not yet a
  complete personal-entity or domain-specific privacy system.
- The MLX training path is machine-specific, and the repository has no small
  portable training backend for CI or hosted demonstration.
- The dashboard reads local run folders. It is not an operational job system
  with durable state, idempotency, retries, or concurrent workers.

## Design principles

### Content-addressed evidence

Dataset versions should be identities derived from source, benchmark, output,
and gate fingerprints. A version label alone is not evidence. This follows the
same core direction as MLflow dataset digests and data-versioning systems.

### Standard metadata, small core

Forge should emit Croissant metadata for interoperability and use PROV-O
relationships for lineage. It should not build a proprietary metadata language
when a public standard can express the same facts.

### Layered quality controls

No single quality score is trustworthy enough. Forge should combine schema
validation, deterministic rules, exact deduplication, MinHash-based fuzzy
deduplication, embedding-based semantic deduplication, contamination checks,
model judgments, and human calibration.

### Evaluation is a separate asset

Evaluation records should not be generated by the same workflow that produces
training targets. The benchmark must have its own source fingerprint, authoring
protocol, version, and access boundary.

### Local first, scale second

Every important control should run locally on a small corpus. Scale adapters
can then target workers, object storage, or distributed processing without
changing release semantics.

## Delivery stages

### Stage 1: Verifiable dataset releases

Status: complete.

Deliverables:

- A versioned release-manifest schema.
- SHA-256 fingerprints for source inputs, benchmark inputs, and artifacts.
- Fail-closed release gates for pipeline completion, artifact integrity,
  benchmark contamination, and source isolation.
- A deterministic release ID that remains stable when the same data is rebuilt
  in a different directory.
- A standalone verifier that detects artifact tampering.
- Croissant 1.1 JSON-LD metadata with PROV-O generation lineage.
- Explicit claim status separating established controls from incomplete human
  and semantic evaluation.

Acceptance criteria:

- A clean run emits `release_manifest.json` and `croissant.json`.
- A modified output file fails verification.
- A contaminated dataset, split overlap, malformed JSONL row, missing input, or
  mismatched artifact hash blocks release.
- All behavior has automated tests and passes CI.

### Stage 2: One pipeline core

Status: core complete. The future HTTP service will call the same API when the
hosted architecture is introduced in Stage 5.

Deliverables:

- Replace script-to-script orchestration with typed stage interfaces.
- Define input and output contracts for ingest, generation, quality, dedupe,
  judgment, contamination, selection, split, training, and evaluation.
- Make every stage idempotent and content-keyed.
- Capture structured start, completion, failure, input, output, model, prompt,
  and configuration events.
- Resume a partially completed run without repeating valid work.
- Rename the Python package to `forge` with a compatibility layer and a
  documented migration.

Acceptance criteria:

- The CLI and tests call `forge.workflow.run_forge`; the future hosted service
  has one supported API to call.
- Re-running identical inputs produces verified cache hits and the same release
  ID.
- Injected stage failure resumes from the last content-verified artifact.

### Stage 3: Real curation and governance gates

Status: core complete. Corpus-specific semantic and privacy calibration remains
part of each candidate release rather than a universal project claim.

Deliverables:

- Exact document and record deduplication.
- MinHash and locality-sensitive hashing for fuzzy duplicates.
- Embedding-based semantic deduplication with calibrated thresholds.
- Layered lexical and semantic benchmark contamination detection.
- PII detection and configurable rejection or redaction.
- Source license and permitted-use metadata.
- Schema validation and per-record quality decisions with reason codes.
- Dataset profile by source, task, length, quality, difficulty, and rejection
  reason.

Acceptance criteria:

- A controlled duplicate corpus measures precision and recall for each dedupe
  layer.
- Paraphrased benchmark examples are detected in a documented test fixture.
- Every rejected record has a machine-readable reason.
- A release cannot pass with unknown source usage rights in candidate mode.

Implemented evidence:

- Document content dedupe runs inside source governance.
- Record dedupe combines normalised exact matching, deterministic MinHash LSH,
  verified shingle Jaccard, and an optional embedding adapter.
- Candidate workflow configuration rejects a disabled semantic backend.
- Benchmark screening combines lexical 8-grams, shingle Jaccard, and the same
  recorded embedding boundary.
- Source and record quarantine files preserve audit decisions and reason codes.
- Candidate releases fail on unknown or disallowed source usage rights.
- Dataset profiles summarise sources, tasks, lengths, quality, difficulty,
  rejections, and artifact hashes.
- A labelled 12-pair control fixture reports precision, recall, F1, and a
  multi-seed bootstrap interval. Its small size is disclosed.

### Stage 4: Independent evaluation and human calibration

Status: engineering framework complete. The independent 200-item human
collection remains the evidence gate.

Deliverables:

- A frozen, independently authored evaluation set with its own release
  manifest.
- A documented annotation protocol and human-reviewed reference subset.
- Blind review so annotators do not see which generator produced an example.
- Agreement metrics such as Cohen's kappa or Krippendorff's alpha, alongside
  calibration error and slice-level results.
- Judge-model versioning, prompt versioning, order randomisation, and bias
  checks.
- Pairwise comparison, deterministic task metrics, bootstrap intervals, and
  multiple training seeds where training claims are made.

Acceptance criteria:

- At least 200 examples are independently reviewed across material task and
  source slices.
- Automatic judge agreement with human labels is published, including failure
  cases.
- No headline result depends on a judge from the same model family used to
  create the targets.
- The benchmark is fingerprinted, frozen, and absent from generator context.

Implemented evidence:

- Evaluation releases are content-addressed and verify every item, protocol,
  packet, review sheet, and blinding-key hash.
- Human packets hide generator identity. Judge packets contain primary and
  reversed candidate order for a direct position-consistency measurement.
- The annotation protocol defines A, B, tie, and both-bad labels, reason codes,
  confidence, pseudonymous reviewers, overlap, and adjudication.
- The analysis reports nominal Krippendorff alpha, two-rater Cohen kappa,
  slice-level pairwise outcomes, a bootstrap win-rate interval, judge agreement,
  macro F1, calibration error, and first-position choice rate.
- The judge runner records provider, model, model family, prompt version, and
  prompt hash. Invalid or unstructured output fails instead of receiving a
  guessed fallback label.
- Claim gates reject fixture-only labels, incomplete coverage, weak agreement,
  poor reversed-order consistency, and same-family judges.
- The eight-item controlled fixture is checked in CI. It validates the machinery
  only and is explicitly excluded from human or model-quality claims.

### Stage 5: Hosted product architecture

Deliverables:

- FastAPI service for sources, jobs, records, reviews, and releases.
- PostgreSQL for metadata and object storage for immutable artifacts.
- A worker queue with job idempotency, bounded retries, cancellation, and
  failure visibility.
- Streaming progress and structured logs.
- A review dashboard that shows lineage, rejection reasons, partition
  boundaries, quality slices, and release gates.
- Authentication, rate limits, safe file handling, secrets management, and
  redacted logs.

Acceptance criteria:

- A recruiter can open one URL, run a bounded public example, and inspect the
  resulting release without creating an account or providing an API key.
- The hosted example invokes the real pipeline rather than duplicating its
  behavior in front-end code.
- Concurrent identical submissions do not create duplicate jobs.
- A worker restart does not lose durable job state.

### Stage 6: Public benchmark release

Deliverables:

- A tagged `v1.0` candidate built from a public, redistributable corpus.
- Reproducible generation and evaluation commands.
- Published release manifest, Croissant metadata, dataset card, human-review
  protocol, results, limitations, and failure analysis.
- Cost, latency, throughput, rejection rate, dedupe rate, contamination rate,
  and quality-by-slice measurements.
- A short architecture walkthrough and a two-minute recruiter demo path.

Acceptance criteria:

- Fresh-checkout workflow passes on a supported machine.
- CI is green on the release tag.
- All public numbers can be traced to immutable artifacts.
- The README presents measured evidence before feature claims.

## Evidence policy

Forge must not claim that generated data improves a model until a release has
an independent benchmark, human calibration, and reproducible training and
evaluation artifacts. Smoke fixtures prove control behavior only. Internal
regression tests prove implementation stability only. Neither proves general
model quality.

## Research basis

- [MLCommons Croissant 1.1](https://docs.mlcommons.org/croissant/docs/croissant-spec-1.1.html)
  defines interoperable dataset metadata and PROV-O provenance relationships.
- [OpenLineage](https://openlineage.io/) models datasets, jobs, runs, and their
  events as a standard lineage surface.
- [MLflow dataset tracking](https://mlflow.org/docs/latest/dataset/) uses source,
  schema, profile, and digest metadata to connect datasets to experiments.
- [Hugging Face dataset cards](https://huggingface.co/docs/hub/datasets-cards)
  document intended use, limitations, license, language, size, and discovery
  metadata.
- [NVIDIA NeMo Curator deduplication](https://docs.nvidia.com/nemo/curator/about/concepts/deduplication)
  separates exact, fuzzy, and semantic duplicate controls.
- [Hugging Face DataTrove](https://github.com/huggingface/datatrove) demonstrates
  composable local and distributed text-processing pipelines.
- [Rethinking Benchmark and Contamination for Language Models](https://arxiv.org/abs/2311.04850)
  shows why string matching alone misses rephrased contamination.
- [Deduplicating Training Data Makes Language Models Better](https://arxiv.org/abs/2107.06499)
  links near-duplicate removal to lower memorisation and cleaner evaluation.
- [SimCSE](https://aclanthology.org/2021.emnlp-main.552/) demonstrates why
  learned sentence representations can support semantic similarity controls.
- [Microsoft Presidio](https://github.com/microsoft/presidio) documents a
  layered privacy design using patterns, checksums, NER, and custom recognisers,
  while explicitly warning that automatic PII detection is not complete.
- [Judging the Judges](https://arxiv.org/abs/2406.12624) shows why model judges
  need human agreement analysis and careful bias controls.
- [Google Data Cards Playbook](https://sites.research.google/datacardsplaybook/)
  frames dataset transparency as a lifecycle and stakeholder problem, not a
  one-time README exercise.
